# Anonymous diagnosis event counts — preparation only

Base production fd7c9c5; dependency update is separate commit 1b92598.
No production SQL, credentials, LOGIN grants, env changes, push or deployment performed.

## Definitions and limits

Only valid POST /api/diagnosis requests reaching the handler after JSON/body/ID validation emit diagnosis_requested. Invalid JSON/ID, other endpoints, health/catalog, and existing feedback do not count. Accepted requests rejected by collector cooldown/capacity etc do count.

At most one terminal event per request: diagnosis_ready means a validated response with five_axis.status === ready emitted Node response finish; diagnosis_withheld means another validated successful result emitted finish; diagnosis_error means an error response (including timeout/collector rejection) emitted finish; diagnosis_disconnected means close happened before writableFinished. Listeners are removed after the first terminal. Default terminal outcome is error, never derived from raw error text. This uses the same ready condition as PublicDiagnosis, not top-level result status.

Response finish means the server handed its response to its transport, not client receipt/JSON validation/UI rendering. Disconnect does not distinguish user cancellation, tab close or network failure. Function kill may emit nothing. Requests that never reach the function are invisible. Repeated clicks, refresh with a new acquisition and retries are separate requests. Ordinary reload loses input and does not automatically request diagnosis. No dedup across tabs/requests/users is attempted. In-memory request booleans are not persisted identifiers.

UTC day is assigned at DB write time, independently for each event; midnight/queue crossing can separate request and outcome. Saved ready/requested and existing saved-feedback-total/ready are event-count ratios, not unique-user conversion or abandonment rates. Ratios can exceed 100% from date boundaries, repeated use, direct API calls, missing writes. The existing three-choice table remains the sole feedback count; no second feedback-success write or identity join.

## Storage and failure isolation

Only day DATE, fixed event TEXT, count BIGINT; no individual row/timestamp/SteamID/IP/cookie/session/URL/history/error body. Maximum normal live shape 30 UTC calendar buckets x 5 events = 150 rows. Today and previous 29 dates kept. Late cron failure may keep older rows until recovery; backups separately retain copies. No guarantee all copies expire in exactly 720 hours.

FYTH_USAGE_ENABLED must equal true to construct its independent pool; off never reads dedicated URI/CA. Existing feedback credentials/target/TLS option validation are reused without touching reader. No new credentials are required by this proposal. pool max1; at most four pending events, serialized; extra work is dropped and never retried. Existing feedback pool max1 + usage pool max1 fits current per-login connection limit2 for a single process, NOT multiple Vercel instances: capacity and pooler behaviour must be reviewed before enable. Timeouts remain connection2s/server2s/lock500ms/query3s. Queue can take up to approximately 12s (plus connection overhead); function duration65s can truncate late work. Missing records are an accepted limitation; cannot promise exact accounting.

waitUntil promises are registered while handling the request, including a terminal-event promise resolved on finish/close; diagnosis does not await metrics. Both synchronous and asynchronous sink errors are swallowed without raw logging and never change diagnosis response. No network/driver retry after uncertain writes. On Vercel waitUntil extends lifecycle within function maxDuration; local tests verify injected registration, not real Vercel suspension/timeout. Bounded writes can fail/drop independently, so requested need not equal terminals. No raw operational error log or individual event buffer.

Owner owns only usage objects; submitter cannot table-read/write/CREATE/expire; maintenance cannot increment/read. Existing feedback application LOGIN initially receives NO new rights. Migration administrator receives SET TRUE / INHERIT FALSE owner/maintenance membership to install objects; PostgreSQL CREATE ROLE may also retain ADMIN OPTION. Review pg_auth_members and this trusted administrator scope, rather than claiming SET is its only privilege. Review target collisions, trusted admin, schema not exposed by Data API and security advisors before applying.

Separate proposed grant, requiring parent/user approval of this exact scope:
