# Connection capacity review (local model only)

Reviewed source base 442aac5; no production credentials, network load, DB grants, role limits, flags or deployment changed.

Current: createRuntimeFeedback and createRuntimeUsage independently construct pg.Pool(max1) using the same fyth_feedback_app_login. Neither pool opens a connection until queried. Reader pool is separate. Per process: feedback up to1 plus usage up to1; per N processes potential2N, not global2. Role connection limit2 constrains PostgreSQL direct/session connections. Actual Supavisor transaction/session pooler settings and backend multiplexing are unverified; client sessions must not be equated with server sessions for every pooler mode.

Both pools: connect/acquisition timeout2s (pg-pool's queued acquisition also bounded), server statement2s, lock500ms, client query3s, idle retention10s. Driver query timeout begins after client acquisition, not usage tail-queue insertion. Feedback API's5s response timer covers its whole store call and can return unknown even if a late commit occurs. No automatic retries.

Usage allows4 pending operations, serializes them, and drops extras. Maximum ordinary tail wait is prior operations' acquisition+query time, potentially3*(2+3)s plus current2+3s; no independent end-to-end per-event deadline. These are timer-budget estimates, not absolute bounds under process suspension/event-loop stall. Function duration65s also cancels waitUntil tasks. Existing handoff's12s+connection-overhead estimate corresponds to4 query3s windows plus acquisition windows; do not call it a total12s bound.

requested and terminal promises are registered during request handling. terminal promise waits for response finish/close but holds no DB connection just by waiting. requested query may open the usage connection; after completion it idles for10s, then closes if timer runs. Terminal later reuses it if still available, otherwise reconnects. Both stages use one usage pool, not one pool each. Concurrent diagnosis events can keep this pool continuously occupied/idle. Frozen/suspended execution may defer ordinary idle cleanup; no real Vercel suspension test here.

Risk: one instance's idle feedback+usage sessions can consume the global2 budget while another instance tries feedback. Then feedback connection acquisition can fail and /api/feedback returns502 unknown; it never promises stored. Thus metrics failure isolation at response/error level does NOT ensure answer-connection isolation. Retention/probe success does not prove capacity under scale.

4 tests in tests/fyth-usage-capacity.mjs passed using a deterministic capacity2 model: independent idle-held usage blocks a third feedback pool; disabled usage preserves baseline two-feedback capacity; a proposed shared pool saves a session; proposed priority gate drops new metrics while answer waits and starts answer before queued metrics. No real driver/network/DB load. The scheduling model is not deployed implementation.

Safe immediate choice: keep FYTH_USAGE_ENABLED unset/false until capacity strategy/runtime checks are approved. No source change is needed for this already-implemented gate. This does not solve pre-existing third-feedback-instance capacity2 limits, but adds no usage pressure.

Candidate local redesign (requires new implementation/review before enable): one aggregate pool max1 per instance shared between answers/metrics, an answer-priority bounded scheduler, drop metrics when answer pending, small end-to-end metrics deadline and appropriate server-side cancellation/client discard. Retain per-event no-retry for uncertain commits. Shared pool alone avoids doubling sessions but still has only global2 total and can delay answers behind a running metric. Priority cannot preempt an already-running query; killing the shared client could turn an answer outcome unknown. Need tests with actual pg mocked client lifecycle/timeouts and staged Vercel behaviour, without pretending local scheduling model guarantees service isolation. Do not silently sample cold starts or label dropped counts as complete funnel counts.

Shorter usage idle timeout or per-event connection teardown alone reduces idle exposure but does not prevent simultaneous connections, may increase handshake rate, and can race terminal/other queued events. It is not sufficient evidence to enable. No increase of connection limit or new LOGIN/credential is proposed here. If rigorous answer isolation at arbitrary instance count is required, current global2 constraint cannot be guaranteed by independent per-process scheduling alone; retain disabled metrics or revisit deployment concurrency/routing separately.
